# Upgrades and migrations

Refaat follows semantic versioning before `1.0.0` with explicit changelog entries, but minor versions may still contain public API changes while the project is in alpha. Pin versions in production.

## Standard upgrade

1. Read `CHANGELOG.md` and migration notes.
2. Build and scan the exact wheel/container digest.
3. Back up relational state and original blobs.
4. Run the candidate against a restored staging copy.
5. Execute the full evaluation suites and representative load tests.
6. Run `alembic upgrade head` once as a controlled job.
7. Deploy API and worker roles from the same application version.
8. Observe errors, leases, outbox, cache routes, latency, and evaluation signals.
9. Keep the prior application image available until the rollback window closes.

## Database compatibility

Do not allow every API replica to run schema creation. Production requires `REFAAT_AUTO_CREATE_SCHEMA=false` and explicit migrations.

For zero-downtime changes, migrations should be expand/contract compatible across the overlapping application versions. Destructive changes need a release-specific plan and tested restore path.

## Migration convention

`alembic upgrade head` is the production upgrade path. The offline runtime and the test suite build the schema directly with `metadata.create_all` (gated by `REFAAT_AUTO_CREATE_SCHEMA`), so tests do not depend on the migration chain.

Every change to `src/refaat/infrastructure/database/schema.py` gets its own incremental revision:

1. Edit `schema.py`.
2. Generate a revision with `alembic revision --autogenerate -m "<change>"`.
3. Review the generated `upgrade` and `downgrade`, fix anything autogenerate misses (partial indexes, server defaults, data backfills), and keep the revision in the chain.
4. Commit the revision alongside the schema change.

Revision `0002_catch_up` reconciles a database that was stamped when `0001_initial` was the only revision. It inspects the connected database and creates only the tables, columns, and indexes that the live metadata defines but the database is missing, so an old database reaches the full current schema while a fresh database sees a no-op. It is idempotent and safe to run more than once. Later schema changes do not extend it; each gets its own revision per the steps above.

The supported production path is the online `alembic upgrade head` run against a live database. An incremental offline SQL delta between two adjacent catch-up revisions (for example `alembic upgrade 0006:0007 --sql`) emits only the version bump and no `CREATE TABLE`, because every catch-up revision from 0002 through 0007 is inspection-driven and no-ops in offline mode; only the base-to-head offline script from 0001 emits the full schema. Do not stamp a database from such an incremental offline delta; run `alembic upgrade head` online instead.

### What 0002 reconciles, and what it does not

The catch-up reconciliation covers a bounded set of object kinds:

- tables that are absent,
- columns that are absent,
- indexes that are absent,
- table-level named unique constraints (created when absent, dropped and re-added when their column set drifted),
- table-level named check constraints (created when absent, dropped and re-added when their expression drifted).

Every other kind of change is out of scope for 0002 general reconciliation and is handled by the going-forward per-change autogenerated revision instead: unnamed or column-level constraints, a foreign key added to a re-added column under SQLite, and column type or nullability drift on an existing column. Reconcile those with a dedicated revision generated per the steps above, not by extending 0002.

### Invariant: a post-0001 NOT NULL column must carry a server_default

A column added to `schema.py` after 0001 that is NOT NULL and has no `server_default` cannot be reconciled onto a populated database: the existing rows have no value for the new column, so the `ADD COLUMN` is rejected. The catch-up refuses such a column with an actionable error rather than emit DDL the database would reject mid-migration. Give any post-0001 NOT NULL column a `server_default` so the reconciliation can backfill it, or add the value in a dedicated data-backfill revision.

## The pgvector schema

The `refaat_chunk_vectors` table, its indexes, and the `vector` extension are provisioned by migration `0012` on PostgreSQL. With `REFAAT_AUTO_CREATE_SCHEMA=false` (required in production) the runtime does not issue DDL: it verifies the extension and table exist and fails startup with an actionable error if they do not, so the application role needs no `CREATE` privilege. With `REFAAT_AUTO_CREATE_SCHEMA=true` (development, tests, the offline single process) the runtime creates them itself, so those paths need no migration step. The migration reads `REFAAT_EMBEDDING_DIMENSIONS` for the vector dimension, the same value the runtime embedder uses, so both agree.

## Embedding model or dimension changes

Vectors produced by different models or dimensions are not interchangeable. Treat the change as an index/data migration:

1. create a new target corpus or index version;
2. replay retained originals;
3. run retrieval and answer evaluations;
4. compare latency, storage, and cost;
5. switch clients only after acceptance;
6. retain the old corpus during the rollback window.

## Generator or graph model changes

Model ID is included in the query cache context. A generator change cannot reuse an old answer cache entry. Even so, run evaluations because answer style, citations, entity extraction, and relation quality can change.

## Plugin upgrades

Plugins are trusted code. Pin package versions and review:

- entry-point names;
- dependency changes;
- filesystem and network access;
- configuration and secret requirements;
- schema or payload compatibility;
- event-sink idempotency;
- cleanup/close behavior.

## Migration safety gate

The `migration_safety` gate statically analyzes every revision under `migrations/versions` and fails the build on a forward operation that would break a running old-code deployment during a rolling upgrade: a NOT NULL column added with no `server_default` (existing rows cannot be backfilled), a dropped or altered column, table, or constraint (a contract step that must follow a prior expand release), or an opaque operation the analyzer cannot verify (a whole-schema build, or a raw SQL statement). A new-table create, and an added column that is nullable or carries a `server_default`, pass. Only the `upgrade` path is analyzed, since a downgrade is a rollback concern governed above. Index creation is treated as safe because the current migrations build indexes on new or empty tables; a large-table index on a busy engine should be created concurrently as a deployment concern, which is out of the static gate's scope.

A revision whose risk is understood and accepted carries a marker comment on its own line, with a required reason the gate prints so the acceptance is auditable:

```
# migration-safety-ack: the reason this forward operation is safe or has a tested plan
```

Use it for a genuinely safe revision the static analyzer cannot prove (the initial full-schema create, or the idempotent catch-up reconciler), or for a deliberate contract or backfill step whose restore path is tested. The gate is fail-closed: a revision it cannot prove safe, and any parse error, fails the build until the change is made safe or the marker is added.

## Rollback

Application rollback is safe only when the prior version understands the current database schema. If not, restore from backup or use a documented down migration that has been tested with real data. Harness rollback is independent: activate a prior immutable snapshot without changing the application version.
